# Dynamic GPU–Hexagon projection experiment

2026-11-10. This is a scratch projection benchmark, not an installed inference backend or a measurement of chat latency.

The GPU computes a maximum absolute activation per token, dynamically quantizes each token to signed Q8 in a shared ION buffer, and hands a row shard to the Hexagon. Concurrently, the GPU computes the remaining rows. A GPU scatter applies the corresponding per-token scale to the DSP result and assembles the output. The measured interval includes the reduction, packing, guard synchronization, FastRPC call, concurrent GPU work, and scatter. Static weight packing, uploading, model loading, and retrieval are excluded. The 128-token test used the real Bonsai 4B layer-0 up weights, deterministic synthetic FP16 activations with token-dependent magnitudes from zero to 8, and 3,072 of 9,216 rows on DSP. Each arm has five timed samples between GPU-only controls.

| Variant, 128 tokens | GPU before | Mixed | GPU after |
| --- | ---: | ---: | ---: |
| Per-token reduction, original pack order | 55.876 ms | 44.123 ms | 55.863 ms |
| Same reduction, adjacent-token pack order | 55.776 ms | 42.982 ms | 55.734 ms |
| Eight-token coalesced reduction and adjacent-token pack | 55.756 ms | 42.220 ms | 55.845 ms |

The last row is about 24% faster than its GPU controls for this projection. In a separate guarded run the same layout took 42.391 ms versus 56.337/56.320 ms at 128 tokens, and 11.851 ms versus 14.392/14.343 ms at 32 tokens. At 16 tokens the mixed path took 7.522 ms versus 7.373/7.377 ms, so the DSP path did not help that case. These results do not imply the same improvement for the complete model.

The input image is stored with adjacent token values together. Reordering the pack work so neighboring work items read neighboring tokens reduced measured packing time in a matched fixed-scale comparison: the candidate had a median total of 41.923 ms, versus 42.997/42.962 ms for bracketing original-layout runs. In one representative sample packing took 3.237 ms versus 4.479 ms before. This trades more scattered output stores for more contiguous reads; it is a measured device result rather than a universal rule.

## Correctness and fallback

GPU-packed bytes matched the CPU reference, shared ION visibility checks passed, the GPU shard matched the GPU baseline bit for bit, and every output passed the scatter check. Against a sampled FP64 reference using the original FP16 values, the 128-token mixed result had normalized RMS error 0.002179384; the GPU result had 0.000973221. At 16 tokens, all 49,152 DSP output integers matched the scalar integer reference. An alternating-input run checked six successive iterations, including warmup, to exercise changed inputs and scales rather than only identical repeated buffers. These tests do not establish model-answer quality. ION host visibility observations are specific to this phone and are not a portable cache-coherence guarantee.

The experimental guard falls back to the complete GPU projection for nonfinite inputs or absolute values above 16. Exactly 16 took the mixed path; the next FP16 value above 16 fell back. Large finite, FP16 extreme, NaN and infinity cases each took six fallback calls, and their non-NaN output bits and NaN masks matched the GPU baseline. The ±16 threshold is provisional and empirical, not a proven bound on FP16 accumulation overflow. The first extreme-input trial without the finite-magnitude guard produced nonfinite GPU-reference outputs; the guarded trial preserved the GPU result instead. Additional checks and a principled policy are required before use in a model.

The current FastRPC request handles at most 128 tokens. The normal texture backend uses up to 256 tokens per microbatch. A separate scratch benchmark addressed that size by packing into two independently aligned shared buffers, dispatching one 256-token GPU shard, invoking two sequential 128-token DSP calls, and scattering the two outputs. The complete timed mixed projection took 85.500 ms versus 112.657/112.705 ms GPU-only at 256 synthetic tokens. This includes reduction, packing, guard, both calls and assembly, but excludes static weight setup. It passed 16,128 sampled scalar DSP checks, GPU-shard bit parity, buffer visibility and alternating-input checks; a large-input fallback matched the GPU baseline. Sampled mixed normalized RMS error was 0.002345354 against 0.0009884313 GPU-only. This is an isolated projection, not a full-model test; the row-view allocation improvement has not yet been combined with this 256-token harness.

The original benchmark creates separate GPU shard weights and a full GPU fallback copy; resident model memory and startup costs must be measured, and shared weight views may avoid duplication.

## Real activation replay and shared GPU weights

A scratch OpenCL interposer captured the first 128 tokens of a 256-token gate/up-shaped activation texture while Bonsai processed one held-out Wiki question and its cached evidence. The test used the production system and user text with approximate chat framing. Before capturing the model input, a synthetic capture matched all 40,960 expected FP16 elements byte for byte. The private model capture was replayed with the layer-0 up weights; the capture shape matches that projection, but the test did not independently prove which layer or sibling produced that activation. Capture and model loading were excluded from projection timings.

The replay took 42.691 ms versus 55.908/55.823 ms GPU-only. The original strict CPU/GPU quantization-byte comparison failed on this input: 113 of 327,680 Q8 values differed by one integer step. GPU-read and host-visible shared buffers matched, every packed block sum was consistent, and the largest distance from ideal real-number quantization was 0.5 Q8 units. Thus the observed discrepancies are consistent with rounding ties; this check is not a proof for other inputs. Recomputing the scalar integer reference from the actual GPU Q8 values passed for all 393,216 DSP outputs. Against the original FP16 inputs and weights, sampled mixed normalized RMS error was 0.00559817, compared with 0.0009796433 for GPU-only.

Two additional held-out prompts were captured and replayed the same way. Their 128-token mixed times were 42.756 and 42.614 ms, against bracketing GPU controls of 55.843/55.910 and 55.742/55.740 ms. Each passed 8,064 sampled scalar DSP integer checks, shared-buffer and block-sum checks, and the ideal quantization-distance bound. Their mixed sampled normalized RMS errors were 0.005777028 and 0.005640334; GPU-only errors were 0.000992439 and 0.0009882659. A complete 256-token activation from the second prompt was also replayed using the two-RPC path: 85.672 ms versus 112.581/112.528 ms GPU-only, with 16,128 sampled scalar DSP checks passing. Its mixed sampled normalized RMS error was 0.005685462 versus 0.0009979574 GPU-only. These are input slices at the first matching projection shape, not model answers or a model-wide error measurement.

An additional GPU row-view variant used the full packed GPU weights for both the baseline and shard and wrote the GPU shard directly into its disjoint destination rows. The DSP scatter wrote only the DSP rows. At 128 synthetic tokens it took 42.403 ms, with its own GPU controls at 56.380/56.374 ms; the separate-shard mixed controls surrounding it took 42.725 and 42.630 ms. This does not establish a clear timing win, but removes the benchmark's duplicate GPU shard allocation. At 32 tokens it took 11.685 ms versus 14.384/14.404 ms GPU-only. Full GPU shard parity, alternating-input checks and a large-input fallback check passed. The row view has not been integrated into the model graph or tested for actual model residency and startup costs.

## Down projection

For the 2,560 × 9,216 layer-0 down projection with 128 synthetic tokens, DSP shards of 256, 512 and 768 rows took 69.430, 80.260 and 110.574 ms respectively, against GPU-only controls of roughly 56.4–56.5 ms. The tested down split is therefore not a candidate for acceleration. Numerical and buffer checks passed for these cases.

The experimental host benchmark is `wiki/experiments/n20-q2-overlap-dynamic-bench.c`; the adjacent-token fixed-scale comparison uses `n20-q2-overlap-shared-coalesced-bench.c`, and the row view uses `n20-q2-overlap-rowview-bench.c` with `n20-q2-activation-image-rowview-prefill.cl`. No phone service or firmware was changed. The tests used the device's idle-checked server stop and shared accelerator lock; the server was restored and the CDSP returned offline with zero recorded crashes.
