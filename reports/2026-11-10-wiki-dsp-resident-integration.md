# Resident DSP matrix integration investigation

The existing v66 RPC dispatcher holds one matrix per handle and replaces it on an upload at offset zero. Re-uploading a shard on every model projection would add work omitted from the projection benchmarks. The experimental `wiki/experiments/v66-q2-rpc-resident.c` adds an opt-in table of 96 matrix slots per session, with select, evict and aggregate stats calls. It limits the requested matrix allocations in one session to 256 MiB, includes alignment padding in its accounting, rejects incomplete uploads at projection, and frees all resident allocations at close. The original dispatcher is unchanged. The caller must serialize all calls through a handle; the extension provides no locking and its limit is per session, not a global device-memory limit.

The dispatcher compiled for Hexagon v66 with Zig 0.15.2 and `-O3 -Wall -Wextra -Werror`. A native host harness with stubbed DSP functions checked partial upload rejection, two independently selected matrices, allocation failure, budget rejection, eviction and close. These are control-flow checks, not proof of device allocation limits or concurrency.

An isolated phone trial subsequently loaded the scratch module through FastRPC, uploaded 3,072 × 2,560 shards from two distinct real Bonsai matrices into separate slots, switched between them, and compared all 49,152 outputs per matrix at 16 tokens against scalar integer references. Slot switching, stats, eviction, incomplete reupload rejection, invalid selection and successful reupload passed. Each resident matrix was accounted as 2,457,727 bytes including alignment allowance; both occupied 4,915,454 bytes. The measured projection calls took 6.407 and 6.496 ms, excluding packing and upload, and are not model timings. This validates two slots on this device, not the 96-slot or 256 MiB limits in practice. The module was not installed; the idle-checked Minecraft service was restored after the test.

A further maintenance trial filled 62 slots of that size, alternating those two real matrices, then switched to slots 0, 31 and 61 and checked their projection results. All 62 completed, with 152,379,074 bytes accounted in the DSP session; every slot was then evicted and the reported allocation returned to zero. Fresh host packing took 318.406 ms, FastRPC uploads 439.930 ms, and the complete fill loop 791.898 ms. The guard observed at least 4,890,060 KiB available memory and at most 27.5 °C battery temperature, restored Minecraft and verified its status; CDSP returned offline with zero crashes. These are one device run with repeated weights and a stopped game server, not a measurement of loading 62 distinct model tensors or live-server memory impact. They establish that this allocation size worked in that session, not that the full 256 MiB limit or simultaneous model residency is safe.

## Memory and placement

The packed DSP format uses 20 bytes per 64 input elements per output row. A 3,072 × 2,560 shard occupies 2,457,600 bytes, and a hypothetical 768 × 9,216 shard occupies 2,211,840 bytes, before up to 127 alignment bytes each. Thirty-two layers with both 3,072-row gate/up shards and a 768-row down shard would therefore request 217.5 MiB plus alignment, within the experimental per-session limit but in addition to the full GPU weights, ION buffers, runtime and operating-system memory. The 768-row down split is an example for capacity planning, not a measured optimal split. This estimate does not establish that the phone, DSP heap or FastRPC implementation can actually sustain that residency. Startup packing/upload time and its effect on available memory need direct measurement.

The original `ggml_backend_opencl_buffer_set_tensor` Q2_0 branch receives the complete row-major tensor before separating and transposing its OpenCL codes and scales. An opt-in integration could pack the DSP shard at that point, record a resident slot and per-matrix scale with the OpenCL tensor extra, and continue building the full GPU weights for fallback. Each tensor extra's reset/destruction, failed upload, context teardown and model reload must release or invalidate its slot safely. A resident entry must not be reused while a queued graph references it.

The activation-texture patch's `ggml_cl_mul_mat_q2_0_f32_adreno` call has the transposed FP16 input buffer, the full GPU weight buffers, destination buffer and destination offset. The split can be attempted there only for supported shapes, layouts and batch sizes; an initial trial can use a 128-token microbatch because the current RPC caps each projection at 128. The row-view kernel and scatter must both honor the destination byte offset and actual destination strides. Unsupported layouts, failed allocation/upload, a nonfinite or out-of-range guard, and failed RPC must retain the complete GPU path. If a shard was already queued when RPC fails, fallback must be ordered after that shard before overwriting the full destination. The same in-order queue and guard-before-shard ordering that were measured in the projection experiment must be verified in the backend, including event ownership and buffer lifetimes.

No whole-model integration patch or end-to-end speedup has been established. Before such a trial, the backend still needs a lifecycle-safe FastRPC client, resident-slot mapping, GPU/ION buffer management, row-view and dynamic scaling kernels, failure recovery and tests against the original graph and real Wiki prompts. Model output and chat-answer quality also need validation because the DSP path is approximate. The earlier synthetic projection result excludes model startup, per-layer residency, retrieval, graph overhead and game activity.
